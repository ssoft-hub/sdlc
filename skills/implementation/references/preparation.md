# Preparing implementation

## Acts of this situation

| Act | An explicit request does not decide it while | Tasks still due on an explicit request |
|---|---|---|
| a strategy under which an element is bought, licensed, taken from the acquirer or from third-party code - a new third-party component the product relies on | the decision contradicts the accepted requirements, architecture, design, coding standard, the conditions of the agreement or of a licence; leaves the deliverable product dependent on a non-deliverable item; a condition of the agreement or of a licence that can be checked before the act is not confirmed | Strategy; Deliverable product of `references/software-item.md` |
| a standard, method, tool or programming language that the project's rules do not yet set | the decision contradicts the accepted requirements, architecture, design, coding standard, the conditions of the agreement or of a licence; leaves the deliverable product dependent on a non-deliverable item | Standards; Deliverable product of `references/software-item.md` |
| acquiring access to an enabling system that costs money or binds the project by conditions | - | Access |

## Preparing for implementation

Outcomes served: constraints identified, element implemented, enabling inputs identified, enabling
systems available.

| Subject | What the agent does |
|---|---|
| Strategy | shall define the implementation strategy, taking into account the disposal constraints on the implementation methods |
| Its decision | should present what it has defined with the output of the work for a decision |
| Its content | should name in the strategy, for each element, whether to build a new one, acquire a new one or reuse an existing one, with or without change, and provide in it for the implementation procedures, the fabrication processes, the tools and equipment, and the uncertainties of an acceptable implementation and of its verification |
| Repeated implementation | should define, for an element implemented again - a replacement, a replica -, procedures that give a stable and repeatable result |
| Standards | shall select, tailor and use the standards, methods, tools and programming languages the organization has documented and established and that suit the work, unless the agreement sets otherwise |
| Technology constraints | should define the implementation of the technology constraints as part of the strategy |
| Constraints | shall identify and record the constraints on the system requirements that follow from the implementation strategy and technology, the characteristics of the architecture, the properties of the design or the implementation methods, and pass them to the system/software requirements definition, architecture definition and design definition processes |
| Their sources | should take into account the current and expected constraints of the technology selected, of the materials, of the elements the acquirer provides or that are adapted, and of the enabling systems of the implementation |
| Enabling systems | shall identify and plan the enabling systems and services of the implementation, and identify the inputs for the requirements for them and for the system elements that serve the implementation |
| Their requirements | should define the requirements for the enabling systems and the interfaces with them, and pass them to the infrastructure management process |
| Access | shall obtain or acquire access to the enabling systems, services and materials to be used |
| Validation | should have the validation process confirm objectively that an enabling system achieves its intended use |
| Life cycle model | shall carry out the implementation work by the project's life cycle model - its stages, goals and outputs -, and, once for the project and at each change of the model, select its activities and tasks, place them in the model and plan them by its stages |
| Model | shall define or select the life cycle model by the scope, size and complexity of the project, where the agreement does not set it |
| The organization's model | should base the project's model on the life cycle model the organization has defined |
| Iteration | may let the activities and tasks of the implementation overlap, interact, and be performed iteratively or recursively |
| Plans | shall develop, record and carry out plans for the implementation work: the specific standards, methods, tools, actions and duties for the development and qualification of all requirements, safety and security included |
| Separate plans | may develop separate plans for parts of the work |
