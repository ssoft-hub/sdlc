# An anomaly, a problem or a defect met

Baselining or changing accepted system or software requirements is an act of the system/software
requirements definition process. Taking or changing an architecture decision is an act of the
architecture definition process. Taking or changing a design decision is an act of the design
definition process. This situation produces the change request each of them receives.

## Acts of this situation

| Act | An explicit request does not decide it while | Tasks still due on an explicit request |
|---|---|---|
| a correction of the accepted requirements, architecture or design that the implementation requires | - | Defect |

## Managing implementation results

Outcomes served: constraints identified, element implemented.

| Subject | What the agent does |
|---|---|
| Anomalies | should name each anomaly by its source - the strategy, the enabling systems, the execution of the implementation, the system definition -, leaving the root cause analysis, the corrective actions, the improvements and the lessons to the project assessment and control process |
| Problems | shall record the problems and nonconformities found in the software products and tasks, and have them resolved by the problem resolution of the quality assurance process |
| Defect | shall name a defect of an accepted output found in the work - a requirement wrong or not feasible, a design incomplete or inconsistent, interfaces that do not match -, with the outputs it affects, and pass a change request to the process that owns that output - the system/software requirements definition, architecture definition or design definition process -, which decides it |
