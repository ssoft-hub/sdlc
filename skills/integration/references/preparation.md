# Preparing integration

## Acts of this situation

| Act | An explicit request does not decide it while | Tasks still due on an explicit request |
|---|---|---|
| an integration strategy that changes the order or the dates set by the project plan | - | Strategy |
| acquiring access to an enabling system that costs money or binds the project by conditions | - | Access |

Changing the dates or the order the project plan sets is an act of the project planning process.

## Preparing for integration

Outcomes served: constraints identified, approach defined, enabling inputs identified, enabling
systems available.

| Subject | What the agent does |
|---|---|
| Coordination | should coordinate integration with the other processes and their checks, so that each interface is achieved, is adequate and takes the needs of integration into account |
| Checkpoints | shall define and record the checkpoints for the correct operation and integrity of the assembled interfaces and the selected functions of the system |
| Their considerations | should consider in them anti-counterfeiting, anti-tamper protection, system and software assurance, and the interoperability of the elements |
| Strategy | shall define and record the integration strategy: the elements the architecture identifies and the order of their combining and testing, by the priorities of the system and software requirements and by the architecture |
| What is missing | should propose what a recorded integration or regression strategy lacks, and present it with the output of the work for a decision |
| Its aim | should make the strategy order the elements by the priorities of the requirements and by the architecture, focus on the interfaces, and reduce the time, cost and risks of integration |
| Its content | should provide for checking an increasingly complete configuration as the elements become ready, for fault isolation and diagnosis, and, where possible, for a human operator, integration, verification and, where appropriate, validation being repeated at each level of the hierarchy until the system is implemented |
| Order | should select the order of combining by the strategy: top-down, bottom-up, critical elements first, by function, a complete skeleton first, or as the elements become ready |
| Plan | shall develop and record a plan for integrating the software units and components into the software item: its test requirements, procedures, data, duties and schedule |
| Regression strategy | shall develop and record the regression strategy: the checks repeated when the elements, the software units, the design or the requirements change |
| Dates | shall obtain the implemented elements at the agreed dates |
| Enabling systems | shall identify and plan the enabling systems and services of integration - build and test environment, simulators of external systems, measuring means -, and identify the inputs for the requirements for them and for the system elements that enable integration |
| Their requirements | should define the requirements for the enabling systems and the interfaces with them, and pass them to the infrastructure management process |
| Their changes | should identify the changes the enabling systems need, and pass the need for them to whoever manages the enabling systems |
| Access | shall obtain or acquire access to the enabling systems, services and materials to be used |
| Validation | should have the validation process confirm objectively that an enabling system achieves its intended use |
| Constraints | shall identify and record the constraints on the system arising from integration that are to enter the system requirements, the architecture or the design, and pass them to the system/software requirements definition, architecture definition and design definition processes |
| Their content | should include in them accessibility for assembly, the safety of those who integrate, the interconnections needed for sets of implemented elements and for enablers, and the interface constraints |
