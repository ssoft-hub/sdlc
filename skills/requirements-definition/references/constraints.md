# Constraints, named implementations and derived requirements

A derived requirement is a requirement that came from no stakeholder but follows from another
requirement or from an accepted decision.

## Acts of this situation

| Act | An explicit request does not decide it while | Tasks still due on an explicit request |
|---|---|---|
| accepting a requirement that dictates an implementation beyond the constraints | - | Named implementation |

## Defining system requirements

Outcomes served: requirements defined.

| Subject | What the agent does |
|---|---|
| Constraints | shall define the necessary implementation constraints |
| Their content | should include in the constraints the implementation decisions that architecture definition allocates at a higher level, those that stakeholder requirements introduce, and those that constrain the solution, such as an accepted platform, a language or a mandatory component |
| Their source | should name for each constraint its source: the process, the requirement or the decision that introduced it |
| Named implementation | shall record an implementation a requirement nevertheless names as a constraint with its source, or present it as the act the table of acts of this file names; this rule governs where the step No implementation of `SKILL.md` meets an implementation already named |
